## Acceptance criteria as actually applied

Gates: `|lmh_relative_difference| < 1e-3`, `|mass_balance_relative_error| < 1e-3`,
`continuity_final < 1e-4`.

The OK set's worst mass-balance error is 2.94e-4. The rejected set's best is
8.58e-3. Classification is the same for any threshold between 3e-4 and 8e-3.

`lmh_relative_difference` has a systematic floor around 1.3e-4 that appears
even on the fully converged empty-channel runs, so it cannot be tightened
below about 3e-4.

Secondary indicator: flatness of `pressure_drop_spacer` over the last 10% of
iterations separates the two sets completely — OK runs are at most 1.0e-6,
rejected runs at least 3.9e-5. LMH flatness does not separate them at all.
This was an observation from this campaign, not a validated general criterion.

## What has been ruled out for the 6 rejected cases

Residuals: only continuity lags, by about five orders. Momentum and species
are at 1e-5 to 1e-6. The last iterations decrease monotonically rather than
oscillating, so this looks like slow convergence rather than a limit cycle.
The advisor's reading is that 0.2 to 0.3 m/s should not be fast enough to
lose steady state, and the data agrees — 25 of 31 geometries converge at
u=0.3.

Restart from the converged u=0.2 solution of the same geometry: tried on
five cases, succeeded on one.

| geo_id | restart u0p3 continuity | result |
|---|---|---|
| S_a144_l1733 | 1.32e-7 | usable; 87th case |
| D2450_a30 | 4.49e-2 | failed |
| D0817_a30 | 2.49e-2 | failed |
| D1225_a30 | 9.25e-2 | failed |
| P_p100_h15 | 7.87e-1 | worse than the original |

The one that worked was the only one whose original `fl_dP` was below 1e-4.
Initial condition is therefore not the cause.

Raising `max_iterations` is not a fix either: the residual decrease rate
itself decays — 0.70% then 0.44% per iteration on D0817_a30.

D0817_a30 restart mass imbalance remains: `m_in` 3.7615e-4 vs `m_out`
-3.7758e-4, relative gap 3.8e-3.

- `pseudo_time_method = {'formulation': {'coupled_solver': 'global-time-step'}}`

template configured. The paper's numerical methods section has to state
the values actually used.

Under-relaxation was never touched: every run logs
`"leaving under-relaxation controls unchanged"` and
`"leaving expert leaf unchanged"`.

## Pseudo-transient: what exists and what does not

`scripts/solver_code_260616.py` never reads or writes pressure-velocity
coupling or pseudo-transient. There is no re-enable after `replace_mesh`.
Iterate-time numerics on the production path are `relaxation_profile=baseline`
(URF untouched), `species_implicit_under_relaxation=preserve`, and
`pseudo_time_verbosity=preserve`.

Only `scripts/batch_solver_rerun.py` has best-effort flags
(`--use-pseudo-transient`, `--coupled`). Those `setattr` calls print a
message and continue on failure rather than raising. The attempted settings
paths are `solution.methods.pseudo_time_method.enabled` and
`solution.methods.pseudo_transient.enabled`. The probe showed `.enabled`
does not exist, so that setattr cannot succeed on 25.1 / 0.38.0. The ramp
strategy also tries TUI `/solve/set/pseudo-transient yes` (and two
near-spellings) best-effort.

Enabling PT on the production path would mean, after `replace_mesh` (or
after a restart `read_case`), turning the `coupled-pseudo-transient`
context back on through a setter that actually exists on this Fluent, then
failing closed if the readback does not show it on. Coupled itself would
not need rewriting; the probe already found `flow_scheme='Coupled'`.

Settings PT would override: explicit pressure and momentum under-relaxation
give way to a pseudo-time Courant number or timescale. Both are currently
Fluent defaults. Production does not write them. Rerun's ramp tries
Courant 20 as a best-effort reduction; that is not on the production path.

Whether species-numerics would come back with PT is unverified. The two
contexts were de-activated in the same `replace_mesh` message. The probe
did not re-enable PT, so it did not observe whether the species-numerics
context reactivates with it. After `replace_mesh` the species-numerics
*leaves* are already the Fluent defaults (linearize all True, threshold
0.1) that all 93 runs used. Template had those leaves False. Whether
re-enabling PT restores the template context, leaves the post-replace
defaults, or does something else was not measured.

PT is not implemented on the production path.

## Infrastructure lessons from the restart work

Four separate plumbing failures, all now fixed:

1. The inlet apply wrote `velocity_magnitude` unconditionally, which is
   inactive when the restart source is already Components.
2. The restart path used the SOURCE case folder as Fluent's working
   directory, so the UDF was compiled from the source `.c` with the old
   `U_TARGET` and report `.out` files were appended to a converged run's
   folder.
3. `/file/set-working-directory` and `(pwd)` do not exist in Fluent 25.1,
   so the fix is to copy the restart source's final files into the target
   leaf as `*_restart_from.cas.h5` / `.dat.h5` and read from there.
4. The transcript parser counted an inherited `"solution is converged"`
   from the source run, recording `max_iter_reached` runs as
   `residual_converged`.

Guards now in place: `U_TARGET` comparison after compile, refusal to write
into the source folder, and a starting-iteration filter on the convergence
marker (first `.out` data line is this session's inherited iteration;
only markers strictly after that count).

Two already-written restart manifests, D0817_a30 and D1225_a30
`u0p3_p6M_restart`, still store `stop_reason=residual_converged` from the
inherited marker. cas/dat were not re-solved. The parser fix does not
rewrite those files.

One outstanding fragility, not fixed: the extract dies with a
`UnicodeEncodeError` on a cp949 console if `PYTHONIOENCODING` is not set,
because a diagnostic string contains an em dash (`whole-domain only — not
for CP c_b` in `scripts/pyfluent_report_extract.py`). It happens after all
computation, just before the CSV write.
